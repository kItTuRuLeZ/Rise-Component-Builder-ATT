# Interactive Video

**Status: Phase 8 of 8 (final documentation/testing/Definition of Done) complete. Feature-complete against the original MVP scope, with one standing exception — see "Definition of Done" at the end of this document.** This document is updated at the end of every phase; only claim what has actually shipped and been tested, per this project's own documentation conventions (`docs/KNOWN-ISSUES.md`, `docs/COMPLETION-INTEGRATION.md`).

## What has shipped so far (Phases 1–7)

A native `<video>` block with a title, optional introduction, optional poster image, optional WebVTT captions, an optional transcript, and an authored, chronologically-ordered list of timestamp-based markers, displayed below the video. Authoring includes a dedicated **Marker Timeline** widget (Builder UI only, Content tab): a live video preview the author can scrub, an "Add Marker at Current Time" action, and a visual timeline track with a clickable tick per marker (text-labeled — "i" / "?" — never color-only) that jumps the preview to that marker and focuses its editor card. Timestamp-specific Preflight rules (near-duplicate markers, markers close to the start/end, markers past the video's own duration, and — new in Phase 3 — a required marker that can never trigger because `pauseVideo` is off) run automatically once the author's preview video has loaded.

In the **exported** component, playback now genuinely pauses at a marker's timestamp — reached either by normal playback (`timeupdate`) or by the learner scrubbing/seeking — and, for an Information marker, opens an accessible interaction panel (title, body, a Continue button) that receives focus and is announced to assistive tech. Crossing detection compares the previous and current playback position on every event rather than testing for float equality against a stored timestamp, so a marker is never missed by landing a frame away from its exact second. If a seek jumps past more than one still-incomplete marker, only the earliest one triggers (preferring an earlier **required** marker over a later one, but never a later one over an earlier required one), and the video is pulled back to sit at that marker's own timestamp rather than left at the seek target. A marker already completed is never re-triggered, and only one marker's panel can be open at a time. Multiple-choice markers already pause and mark themselves visited (never silently skipped) even though their own answer-selection panel is Phase 4 work — they currently just have no panel yet.

Completion rule wiring is real: `videoEnded`, `allRequiredInteractionsCompleted`, and `videoEndedAndRequiredInteractionsCompleted` are all evaluated using genuine per-marker completion state, not just the `videoEnded`-only stub from Phase 1. `resumeBehaviour` (`manual`, `automaticAfterInformation`, or — new in Phase 4 — `automaticAfterCorrectAnswer`) governs whether playback resumes on its own once a marker's panel is dismissed.

Multiple-choice markers now have a real answer panel: the authored question, a keyboard-operable custom radiogroup of up to 4 answer options (arrow keys/Home/End move and select, matching `multiple-choice.js`'s own established roving-tabindex pattern), and an explicit Submit button — selecting an option never silently auto-submits. Submitting resolves feedback with a "specific overrides general" precedence (an answer's own `answerNFeedback` if authored, else `generalCorrectFeedback`/`generalIncorrectFeedback`, else a plain default), tracks attempts against `maxAttempts`, and only concludes the question — disabling further input and marking the marker `completed` once the learner clicks the resulting Continue button — once the learner answers correctly or exhausts their attempts. An incorrect attempt with attempts remaining keeps the panel open for a retry and reveals the authored hint (if any); an exhausted incorrect attempt optionally reveals the correct option (`showCorrectAfterFinal`). `resumeBehaviour: 'automaticAfterCorrectAnswer'` auto-resumes playback after Continue only when the concluding answer was correct — an incorrect-exhausted conclusion always leaves playback paused regardless of `resumeBehaviour`, since auto-resuming away from unresolved wrong feedback would be poor UX.

The marker list is now a live, learner-facing navigation control, not a static preview. Both `showMarkerNavigation` and `showVideoProgress` — authored since Phase 1 but never actually wired until now — are independently honored: `showMarkerNavigation` gates whether the clickable list itself renders, `showVideoProgress` gates a component-own "N of M completed" summary (distinct from the shared, project-level "Progress Completion" percentage bar every `trackCompletion`-enabled component already gets). Each marker row shows a live state badge — `Visited`, `Completed`, or (Multiple Choice only) `Correct`/`Incorrect` — text-labeled, never color-only, updated the moment that marker's status changes. Clicking a row jumps the video to that marker: if not yet completed, it pauses there and opens the marker's own panel (regardless of that marker's own `pauseVideo` setting, since a deliberate click is a different act from automatic crossing-based triggering); if already completed, it just seeks there without reopening anything, matching the existing "never re-trigger a completed marker" rule.

`allowRestart` now renders a real Restart control: it clears all marker/attempt state, returns the video to 0:00, and resets the component's own local progress display. It deliberately never touches `RiseComponentCompletion`'s one-way `hasCompleted()` flag or attempts to un-send the `'complete'` message already given to a host — there is no "un-complete" in Rise's documented completion contract, matching `multiple-choice.js`'s own existing reset-then-retry precedent. Concretely: after a restart, the shared completion **message** stays hidden even once the learner re-completes everything (that part of the shared mechanism is a genuine one-way gate, not something this component can or should override), but this component's own progress bar/text and marker-list badges do update again, so the learner's local sense of progress isn't stuck showing 100% after they've asked to start over.

Phase 6 ran a real, automated accessibility audit against the compiled component (`@axe-core/playwright`, matching this repo's own established `tests/e2e/accessibility.spec.js` pattern) across several learner-facing states, plus keyboard-traversal and reduced-motion checks. It found and fixed one genuine bug in code from this feature: `.iv-panel-type-label` used `var(--accent)` (the AT&T brand blue) at small bold size, which only reaches ~3:1 contrast on a white card — short of WCAG AA's 4.5:1 for non-large text. Changed to `var(--text-muted)`, which also fixes an internal inconsistency (`.iv-marker-nav-title`/`.iv-marker-type-label` in this same file already used `--text-muted` for the same kind of small caption label). See "Known limitations" for a related, pre-existing, out-of-scope finding in the shared export shell.

Phase 7 shipped the two remaining MVP QA items. A new Preflight rule, `interactive-video-non-direct-video-url`, now Blocks export when an External Video URL's hostname is a known video-hosting page (YouTube, `youtube-nocookie.com`, `youtu.be`, Vimeo including `player.vimeo.com`) rather than a direct media file — a native `<video>` element cannot play a hosting-page URL at all, so this meets the same "output would be fundamentally unusable" bar every other Blocking rule uses. And three ready-to-import sample projects now exist under `docs/examples/interactive-video/` (see "Sample configurations" below) — this app has no preset-picker UI to plug a demo system into, so a "documented sample configuration" is a plain project JSON file opened through the Builder's own existing Import Project File flow, not a new feature.

Phase 8 was a full-project regression pass (every unit test, every e2e test across the whole application, not just this component — nothing else in the app drifted across 7 phases of changes) plus a documentation accuracy sweep: several other docs (`docs/ARCHITECTURE.md`, `docs/EXPORT-CONTRACT.md`, `docs/KNOWN-ISSUES.md`, `docs/TESTING-STRATEGY.md`, `docs/RISE-COMPATIBILITY-MATRIX.md`, `docs/MEDIA-ASSET-PIPELINE.md`, `docs/COMPONENT-SCHEMA.md`) still said "20 components" or omitted Interactive Video from a component list/table entirely, left stale by this feature's own additions — all fixed. See "Definition of Done" at the end of this document for the full, honest accounting of what is and isn't actually done.

The Marker Timeline widget remains a **Builder authoring tool only** — it has no equivalent in the exported component and is never part of any export output.

## Instructional use cases (why this differs from Rise's native Video block)

Rise's own Video block plays a file with standard controls and nothing else. Interactive Video is meant for content where the video *is* the lesson, not just supporting media: a compliance walkthrough with required checkpoints, a software demo with step call-outs, a product tour with a comprehension check at the end. None of that is buildable with Rise's native block.

## Authoring workflow (Phase 1 scope)

1. Add "Interactive Video" from the **Advanced Interactions** catalog category.
2. **Content tab → Video Details**: choose Video Source (Uploaded video or External direct video URL), set the source, optionally add a poster image, WebVTT captions, and a transcript.
3. **Behavior tab → Playback & Completion**: resume behavior, completion rule, and which learner-facing elements (marker list, progress summary, Restart) are shown — all genuinely wired as of Phase 5, not just rendering scaffolding.
4. **Marker Timeline** (Content tab, above Interactive Items): scrub or play the video preview, then click **"+ Add Marker at Current Time"** to create a marker at the exact playhead position (rounded to the nearest second) — the primary, recommended workflow. Click any tick on the timeline track to jump the preview back to that marker and open its editor card.
5. **Interactive Items**: markers can also be added via "Add Item" and their Timestamp typed manually in seconds — both paths are fully supported, per the MVP requirement not to force manual timestamp entry as the *only* way. Each marker has a Type (Information / Multiple Choice), Timestamp, Title, Required, Pause Video, and the full field set for both marker types — both sets are always visible regardless of which type is selected; this editor has no conditional field visibility (`docs/COMPONENT-SCHEMA.md` "Recommended schema improvements"), a known, accepted trade-off already present throughout this codebase's Guided-mode features. Fields not relevant to the marker's current Type are simply unused by the generator.

Edit, duplicate, delete, and reorder markers all use the existing generic item editor — no marker-specific code was needed for those, they came from the schema alone.

## Supported video sources

- **Uploaded video**: reuses the existing IndexedDB media system exactly as `video-frame.js`/`audio-player.js` already do — `mp4`/`webm` only, validated by file signature, not just extension (`js/media.js`). The project JSON only ever stores a reference (`{source:'upload', mediaId, ...}`), never the file itself.
- **External direct video URL**: any `http(s)` URL, validated by `sanitizeURL`. A known video-hosting page (YouTube, `youtube-nocookie.com`, `youtu.be`, Vimeo) is rejected at Preflight/export time (`interactive-video-non-direct-video-url`, Blocking — see "Timestamp and URL validation" below), not just warned about in the field's own label text.

## Media-storage and export behavior — read before using uploaded video

This is a **pre-existing limitation of the whole application**, not something introduced by Interactive Video — `video-frame.js` and `audio-player.js` already have it today. Documented here in full because the MVP brief specifically asked for this to be traced precisely rather than assumed.

`js/export.js#prepareMediaExport()` only inlines a small (≤1MB), non-SVG **image** as a `data:` URL. Video, audio, and captions are never inlined — in the **Iframe Snippet** and **HTML Block Fragment** export formats (both `mode: 'inline'`), an uploaded video/captions reference becomes a bare `assets/<filename>` relative path with no way to actually deliver that file alongside the pasted snippet. Rise has no concept of a sibling `assets/` folder for a pasted code block, so that path will 404 once pasted.

**The only export path with a real, recorded pass in Rise for media-bearing components** (`docs/COMPATIBILITY-RESULTS.md`, 2026-08-12) is: export **Web Package ZIP**, extract it, host `index.html` + `assets/` externally, then iframe-embed that hosted URL in Rise. A Preflight Warning (`interactive-video-uploaded-media-export-format`, Phase 7) now recommends this path proactively whenever an uploaded video and/or uploaded captions file are present, rather than leaving the author to discover the 404 only after publishing with the wrong format.

**External direct video URL avoids this problem entirely** — nothing needs packaging, since the file is already hosted wherever the author put it.

## Marker data model

Component-level fields: `title`, `introduction`, `videoSourceType`, `videoMediaId`, `videoUrl`, `posterImage`, `posterAltText`, `posterDecorative`, `captionsUrl`, `captionsLabel`, `transcript`, plus behavior fields `resumeBehaviour`, `completionRule`, `showMarkerNavigation`, `showVideoProgress`, `allowRestart`. Field names deliberately match `video-frame.js`'s existing conventions (`posterImage`, not `posterMediaId`) rather than introducing new terminology — see the schema comment in `js/editor-schemas.js`.

Each interaction marker (`items[]`, `minItems: 0` — a video with zero markers is a complete, valid configuration): `type` (`information`|`multipleChoice`), `timestamp` (seconds), `title`, `required`, `pauseVideo`, `continueButtonLabel`, and both type-specific field sets always present: `body` (information); `question`, up to 4 flat answer slots (`answer1Label`…`answer4Label`, `answer1Feedback`…`answer4Feedback`), `correctAnswerIndex`, `generalCorrectFeedback`, `generalIncorrectFeedback`, `hint`, `maxAttempts`, `showCorrectAfterFinal` (multiple choice).

**Known limitation, deliberate**: multiple-choice answers are capped at 4 flat slots rather than an unbounded list. The schema-driven item editor (`js/editor.js`) has no field type for a nested, repeatable sub-list within an item — every field is scalar. A fixed slot count was chosen over a delimited-text encoding (used elsewhere in this codebase, e.g. `pricing-comparison.js`'s `•`-split feature list) as the lower-risk, more consistent option. Revisit only if a real authoring need for a 5th+ answer emerges.

## Completion (Phase 3 scope)

Internal to this component only — never described as Rise, LMS, SCORM, or course completion, per `docs/COMPLETION-INTEGRATION.md`'s own established framing. All three completion rules are now genuinely wired: `videoEnded` (video reaches its end), `allRequiredInteractionsCompleted` (every marker with `required:true` reaches `completed` status), and `videoEndedAndRequiredInteractionsCompleted` (both). A marker only becomes `completed` when the learner actually dismisses its panel (clicks Continue) — merely being triggered/shown marks it `visited`, not `completed`, and `visited` alone never satisfies `allRequiredInteractionsCompleted`.

**A real bug was found and fixed while building this**: the shared cross-component progress/completion mechanism (`js/export-shell.js#updateProgress`) treats `viewedItems.size / totalItems` reaching 100% as completion and fires the shared completion message unconditionally when it does. Early in Phase 3, marking a marker merely *visited* (triggered) added it to that shared `viewedItems` set, so a video with a single required marker hit 100% — and fired completion — the instant its panel opened, before the learner had done anything. The fix: only a genuine marker *completion* (Continue clicked, or a multiple-choice attempt resolved once Phase 4 exists) is added to `viewedItems`/reflected in the shared progress bar; per-marker `visited` state is tracked separately in an internal map that never touches the shared completion path. This makes the progress bar read "N of M markers completed," which is also the more honest reading of "progress" than "N of M merely seen."

**A second, related real bug — found from actual production use, after Phase 8** — had the same root cause one layer deeper: `updateProgress()` doesn't just update the visible progress bar, it *also* unconditionally calls `evaluateComponentCompletion(percent)`, firing the shared completion signal to the host the moment `viewedItems.size` reaches `totalItems` (the marker count for this component) — completely independent of, and blind to, `completionRule`. A video configured for `completionRule: 'videoEnded'` with one or two markers would report complete to Rise the moment those markers were completed, even though the video hadn't ended and the author had explicitly asked for "watched to the end." `ivEvaluateCompletion()` was already correctly rule-aware (it only ever calls `updateTrackerComplete()` when the *actual* configured rule is satisfied) — the bug was that the shared, generic `updateProgress()` gave the component a second, rule-blind path to the same completion signal, purely as a side effect of also wanting to keep the progress bar's percentage display in sync. Fixed by introducing `ivDisplayProgress()` — the same percent/bar/text/ARIA update `updateProgress()` does, but without ever calling `evaluateComponentCompletion()` itself. `ivEvaluateCompletion()`/`updateTrackerComplete()` is now the *only* path that can ever report completion for this component, exactly matching what `completionRule` says. Covered by two new e2e regression tests (`tests/e2e/interactive-video.spec.js`): completing every marker under `videoEnded` and under `videoEndedAndRequiredInteractionsCompleted` must not fire completion, only actually reaching the end (and, for the latter, also completing the required marker) may.

**Restart and the completion message (Phase 5)**: `js/export-shell.js#evaluateComponentCompletion` gates the completion message on `RiseComponentCompletion.hasCompleted()`, a flag that only ever goes false→true and is never reset — by design, since a host already told `'complete'` (`js/completion.js`) should never be told otherwise; there is no "un-complete" in Rise's documented completion contract. This means once a learner has completed the video once, Restart-then-redo will correctly update this component's own progress bar/text and marker-list badges again, but the completion message paragraph itself stays hidden — a shared, deliberate, cross-component behavior (also true of `multiple-choice.js`'s own "Try Again" reset), not a gap specific to this component.

## Accessibility (Phases 3–6)

- Native `<video controls>` — no custom playback controls exist or are planned to replace them.
- Never `autoplay`; never forced-on captions (no `default` attribute on the `<track>` unless a learner or author explicitly enables it — no such toggle exists yet).
- Transcript is a native `<details>/<summary>` disclosure — genuinely keyboard-operable and exists in the document with zero JavaScript required, satisfying "must not be dependent on JavaScript to exist."
- Marker type is conveyed with an icon **and** a visible text label (Information / Multiple Choice), never icon- or color-only.
- A marker's live state (Visited/Completed/Correct/Incorrect) is a text badge, not a color-only indicator; the currently-open marker also gets `aria-current="true"` on its own nav button, a real semantic signal for assistive tech, not just a visual highlight.
- Each marker-list row is a genuine `<button>` (not a styled `<div>`), so it's keyboard-operable (Tab/Enter/Space) with no custom key handling needed for the row itself.
- The interaction panel is a `role="region"` with `tabindex="-1"`, receives focus programmatically the moment it opens, and is announced via the existing shared live-region `announce()` helper (title plus a plain-text-stripped summary of the body).
- The Multiple Choice answer list is a hand-built `role="radiogroup"`/`role="radio"` pattern (no native `<fieldset>`/`<input type="radio">`, since the visual design needed full styling control) — verified by axe-core's `aria-required-children`/`aria-allowed-role` rules, not just assumed correct.
- Plain-text marker fields (title, Continue button label) are escaped at the point of DOM insertion via a small client-side helper, not pre-escaped at the compile-time sanitization boundary — this avoids double-escaping against the existing server-side `escapeHTML()` calls already used by the static marker-list rendering shipped in Phase 1. Rich-text fields (`body`, the Phase-4 `question`) are sanitized once, at the compile-time boundary, since the richtext sanitizer is Node-only and unavailable client-side.
- Focus indicators on this component's own new interactive elements (marker-nav buttons, MC options, Submit/Continue/Restart) rely entirely on the shared shell's global `:focus-visible` outline rule (`js/export-shell.js`) — verified visible (≥2px outline) and that `prefers-reduced-motion: reduce` collapses this component's own CSS transitions, via a dedicated Phase 6 test.
- **Confirmed, not assumed**: keyboard Tab traversal reaches every one of this component's own controls (marker-nav buttons, Restart) without getting stuck. Native `<video controls>` itself has several of its own internal (shadow-DOM) focus stops — play, scrubber, volume, fullscreen — which is normal browser behavior this component doesn't and shouldn't try to override, not a defect.

## Responsive behavior

16:9 `aspect-ratio` video container, no fixed pixel dimensions. Marker list wraps its title text on narrow screens (`≤480px`) rather than truncating or overflowing.

## Marker Timeline widget — how duration is known

`config.videoDurationSeconds` is a runtime fact, not something an author types in — it's captured automatically from the Marker Timeline widget's own `<video>` element's `loadedmetadata` event (`app.js`) and stored with the project so it round-trips through save/load/import-export like any other field. It resets (briefly, until the next `loadedmetadata` fires) whenever the configured video source actually changes. The timestamp QA rules below degrade gracefully — not falsely — when this value isn't known yet: they simply don't run the duration-dependent checks, the same "unmeasured, not failed" convention `js/dom-measurement.js`'s clipping-risk rules already established for a different runtime-only fact. (Audit 2026-09-30, section 3: when the widget has not measured the video, the timestamp rules fall back to the uploaded file's own recorded length, `videoMediaId.duration`, read at upload time, so a project checked from QA or export without opening the editor is still verified. With neither, `interactive-video-duration-unknown` (Recommendation) says the markers are unverified instead of letting the missing warning read as a pass.)

## Timestamp and URL validation (Phases 2–3, 7)

Six Preflight rules, scoped to `interactive-video` (`js/validation.js`), all Warning severity except where noted — full detail and rationale in `docs/VALIDATION-RULES.md`'s own "Interactive Video rules" section:

- **Near-duplicate timestamps** — two markers within 1 second of each other (they'd be hard to trigger independently once playback pausing exists).
- **Marker near the start or end** — within 2 seconds of `0:00` or of the known video duration.
- **Marker outside the video's duration** — Warning normally; **Blocking** when the marker is also marked Required, since a required marker that can never trigger means the video could never be completed.
- **Required marker that never pauses** — `required:true` combined with `pauseVideo:false`. Warning, not Blocking: the marker-nav list (Phase 5) can still open it via a deliberate click regardless of `pauseVideo`, so this is only truly unreachable when `showMarkerNavigation` is also off.
- **Non-direct video URL** (Phase 7) — **Blocking.** `videoUrl`'s hostname is a known video-hosting page (YouTube, `youtube-nocookie.com`, `youtu.be`, Vimeo) rather than a direct media file. A native `<video>` element cannot play it at all, so the export would show no video whatsoever — the same "fundamentally unusable" bar every other Blocking rule in this app uses.
- **Uploaded video/captions need Web Package ZIP** (Phase 7) — an uploaded video and/or uploaded captions file are present. See "Media-storage and export behavior" above.

`components/interactive-video.js`'s own `validate()` (Phase 1) is unchanged: it still only blocks on a missing video source, a missing marker title, a negative/non-numeric timestamp, and marker-type-specific required content. The six rules above intentionally live in the registered-rule QA system, not `validate()`, matching how `hotspots`' out-of-range-position and overlap checks already work — `validate()` is deliberately built as fast, defaults-obvious authoring correctness gates, while duration-dependent, cross-marker, and export-format checks belong in Preflight.

## Two real bugs found and fixed from production use (post-Phase-8)

Both were reported after the 8-phase build was already complete and committed — real usage surfacing what the automated test suite hadn't.

**1. Completion firing the instant every marker was completed, regardless of `completionRule`.** With `completionRule: 'videoEnded'` and only one or two markers, completing those markers reported the component complete to Rise even though the video hadn't ended. Root cause: the shared, generic progress mechanism every simple component relies on (`js/export-shell.js#updateProgress`) auto-fires completion whenever `viewedItems.size` reaches `totalItems` (the marker count here) — completely blind to this component's own configurable `completionRule`. `ivEvaluateCompletion()` was already correctly rule-aware; the bug was that the shared function gave the component a second, rule-blind path to the same signal, purely as a side effect of keeping the progress bar's percentage in sync. Fixed by introducing `ivDisplayProgress()` — the same bar/text/ARIA update, without ever calling `evaluateComponentCompletion()` itself; `ivEvaluateCompletion()`/`updateTrackerComplete()` is now the only path that can report completion. Two new e2e regression tests cover `videoEnded` and `videoEndedAndRequiredInteractionsCompleted` specifically not firing from completed markers alone.

**2. The live Builder preview rendering completely blank on the very first component selection in a session** — but correctly on every subsequent switch between components, and correctly after a full page reload. Root cause (`app.js#updatePreviewEmptyState`, a shared mechanism every component goes through, not something in `interactive-video.js` itself): the preview iframe's `hidden` attribute is removed and its `srcdoc` is written in the same synchronous tick, back to back. For a sandboxed (no `allow-same-origin`) iframe, some Chrome builds haven't finished a layout pass for the newly-unhidden subtree by the time the `srcdoc` navigation starts, so its very first paint is silently dropped until an unrelated later reflow happens to repaint it — self-resolving almost instantly for a small/fast component (never noticed in 8 phases of testing other components), but leaving a larger payload with its own external media indefinitely blank, since nothing else naturally triggers a reflow while the author is just looking at it. Fixed with a forced synchronous reflow (`void livePreviewIframe.offsetHeight`) between unhiding the iframe and writing its content, applied only on that specific hidden→visible transition. Verified by hand (3 clean reproductions before the fix, 3 clean passes after, via a real browser with `localStorage` cleared each time) and by a new dedicated e2e test (`tests/e2e/application.spec.js`) that selects Interactive Video as the literal first interaction on a fresh page — distinct from the pre-existing comprehensive "every component" smoke test, which (a related gap, also fixed) never actually included Interactive Video at all, since its `advanced` category key had never been added to that test's category list, and which only ever exercises this component as a *switch* target regardless, never as the true first selection.

## Known limitations

- **Found in Phase 6, not fixed here — out of this component's own scope**: `js/export-shell.js`'s shared `.block-label` ("SAMPLE EXPORT" / the block's category label above every exported component's title) has the identical `--accent`-at-small-bold-size contrast issue that `.iv-panel-type-label` had before this phase's fix — axe-core flagged it during this audit, excluded from this component's own test scope (`.exclude('.block-label')` in `tests/e2e/interactive-video.spec.js`) since it's shared chrome every component gets, not something `interactive-video.js` owns or can fix alone. Worth a follow-up ticket scoped to the shared shell/theme tokens, not bundled into this feature's own changes.
- `ivMcAttempts` (per-marker attempt counts) persists in memory for the life of the page view even if a learner seeks away from an in-progress, not-yet-concluded Multiple Choice marker and later re-triggers it — by design, so a learner can't get free extra attempts via seek-away-and-back, but there is no explicit UI telling the learner "you have N attempts left across visits" versus "per visit." Restart clears it, per marker.
- After a Restart, the shared, project-level completion **message** never reappears even once the learner re-completes everything — this is deliberate, one-way behavior shared by every component with `trackCompletion` on (see "Completion" below), not something specific to (or fixable within) this component.
- There is no guard against a learner using the native `<video>` controls' own scrubber to seek away from an open interaction panel mid-decision — the panel stays open and playback stays paused (the panel's Continue button is still the only way to dismiss it), but this hasn't been given dedicated UX treatment. Revisit if real usage shows it's confusing.
- The non-direct-video-URL check (Phase 7) is a short, explicit hostname list (YouTube, Vimeo, and their common variants), not a general "is this a direct file" detector — a URL from a hosting service not on that list still passes silently. Extend the list if a real, recurring authoring mistake with a different service surfaces.
- The Marker Timeline widget's duration capture depends on the author's own browser successfully loading the video's metadata — an unreachable external URL or an unsupported format leaves `videoDurationSeconds` unset and the duration-dependent rules simply don't run (not a false pass, an honest "not measured yet").
- Not yet manually verified inside Rise's own authoring preview or a published course — see `docs/RISE-TEST-CHECKLIST.md`. Do not describe Rise compatibility as confirmed until that happens.

**Real bugs found and fixed via this e2e suite:**
- **Phase 4**: the Submit button was initially given both `.iv-mc-submit-btn` and the shared `.iv-continue-btn` class for quick visual reuse. ## Phase 8: full-project regression pass

Everything above is this component's own tests. Phase 8 additionally ran the **whole application's** test suite — not just Interactive Video's — since 7 phases of changes touched shared, cross-component files (`js/export-shell.js` was read but never modified; `js/validation.js`, `js/component-registry.js`, `js/editor-schemas.js`, `app.js`, `index.html`, `styles.css` were all extended, never had existing behavior changed) and the only way to be sure nothing else drifted is to actually run it:

- Full `vitest run` (all 28 test files, every component, not filtered to Interactive Video) — **814/814 passed.**
- Full `npx playwright test` (every e2e spec — accessibility, editor, export, media pipeline, preflight, every other component's own interaction tests — across chromium/firefox/webkit, not filtered) — **475 passed, 44 failed, 6 skipped.**
- `npm run lint`, `npm run build` — both clean.

**The 44 full-suite e2e failures were investigated, not just noted.** Only a handful named `interactive-video.spec.js`; the rest were spread across `interactions.spec.js`, `persistence-export.spec.js`, `preview-device-modes.spec.js`, `editor-preview.spec.js`, `application.spec.js`, `full-journey.spec.js`, `preflight.spec.js`, and `project-safety.spec.js` — files with zero code overlap with anything touched across all 8 phases (confirmed: `git diff --stat` on every shared file this feature touched — `app.js`, `index.html`, `styles.css`, `js/utilities.js` — shows purely additive changes; the only near-exception, one modified import line in `app.js`, is itself additive). This pattern (widely scattered failures in unrelated features, concentrated in firefox/webkit) matches a **pre-existing, already-documented** condition: `docs/TESTING-STRATEGY.md` "E2E browser matrix and known flake" already records a firefox launch-latency flake in this environment, and explicitly states `npm run validate` deliberately excludes `test:e2e` for exactly this reason. Rather than take the documented flake on faith, it was verified directly: `git stash` reverted every Interactive Video change (the untracked new files, including `interactive-video.spec.js` itself, are unaffected by a plain `git stash`), `project-safety.spec.js` — one of the failing files — was re-run against that clean, pre-Interactive-Video baseline, and **all 12 of its tests passed**, including the specific ones that failed under full-suite load. `git stash pop` restored the work immediately after, verified intact (`git status`/`git diff --stat` unchanged, 814/814 unit tests still passing). Interactive Video's own e2e suite was then re-run cleanly in isolation post-restore: **99/99 passed.** Conclusion: the 44 failures are full-suite resource contention (many browsers/workers competing on one machine) plus the already-documented firefox flake, not a regression introduced by this feature.
